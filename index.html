Personal project

Terraform EKS Platform

A production-style AWS platform in Terraform, designed to be created for an afternoon and destroyed afterwards.

The repository is built to stand up the pieces a real platform team owns: S3 remote state with native locking, a VPC, EKS with IRSA and access entries, plan-on-PR CI through GitHub OIDC with no stored keys, Trivy scanning, and Flux for GitOps delivery.

I built it with Claude as a coding assistant. I ran and reviewed every stage myself.

Read the code on GitHub

How the platform fits together

  1. State
  2. Network
  3. Cluster
  4. Identity
  5. CI
  6. GitOps

  1. Remote state

    A separate bootstrap/ stack, on local state, creates the S3 bucket that holds every other stack's state: versioned, encrypted, public access blocked, and locked with Terraform's native S3 lockfile, so there is no DynamoDB table to run.

  2. Network

    A VPC on 10.0.0.0/16 across two availability zones. Every pod takes a VPC address, so the private /20 subnets get the room; the public /24s hold the NAT gateway and load balancers. One NAT gateway keeps cost down, and an S3 gateway endpoint keeps image pulls off it.

  3. Cluster

    EKS with a managed node group on Amazon Linux 2023 in the private subnets: one t3.medium that can scale to two. The API has a private endpoint and a public one limited to allow-listed addresses. Add-ons: vpc-cni, kube-proxy, coredns and the EBS CSI driver.

  4. Identity

    Authentication runs on access entries only, with no hand-edited aws-auth ConfigMap: one admin principal gets the cluster admin policy. IRSA is on, and the EBS CSI controller is the worked example: its service account token is exchanged for its own IAM role.

  5. CI through GitHub OIDC

    Pull requests run fmt, validate, tflint and a Trivy scan, then a read-only plan posted as a comment with account IDs and IPs redacted. Plan and apply use separate short-lived roles; apply runs only from main, after approval in the dev-apply environment. No AWS keys are stored, and destroy never runs in CI.

  6. GitOps with Flux

    Flux's source and kustomize controllers pull a separate GitOps repository over a read-only deploy key and compare the cluster with Git every minute. It is a separate repository so Flux's commits do not collide with branch protection on the platform repo; podinfo is the demo app.

Built to be destroyed

Nothing is meant to run overnight. The teardown has a set order: suspend Flux and remove the apps, destroy the platform, then the CI access, and last the state bucket, which needs a deliberate code change before it can go.

PR Guardian Action

In progress, release candidate

A generic GitHub Action that reviews pull requests touching Terraform, Kubernetes YAML, workflows and Dockerfiles.

A rules engine does the reviewing and leaves inline comments on the lines that need attention. An optional AI layer can add notes on top, and it is built so that it never fails a check on its own.
